Новый алгоритм (текущая версия) — максимально подробно
Ниже я распишу ровно то, что сейчас реализовано в сервере в режиме algo_new после последней правки: “первый запрос — как OLD, дальше — сглаживание маленьких остатков”.

1) Что сервер вообще пытается сделать
У нас есть две шкалы времени:

Cs — серверное “сейчас”

time_local: аптайм сервера в мс от clock()
time_ntp: Unix‑время в мс от 01.01.1970 (локальные часы ОС + ntpTimeOffsetMs)
Cc — клиентский счётчик (клиент сам его ведёт)

стартует с 0
после каждого ответа: Cc += correction
после задержки Tc: Cc += Tc
Сервер хочет прислать такое correction, чтобы клиентский счётчик приближался к Cs.

2) Сырая ошибка (одинакова для OLD и NEW)
На каждом входящем UDP‑запросе сервер вычисляет:

[ raw = Cs - Cc ]

Где:

(Cs) — значение времени на сервере “в момент обработки”
(Cc) — то, что клиент прислал в GETSINCHRO.curvalue
Смысл raw:

raw > 0: клиент отстаёт, надо прибавить
raw < 0: клиент “убежал вперёд”, надо прибавить отрицательное (т.е. уменьшить)
3) Проблема старого “EMA по raw” (почему мы его переделали)
Когда клиент стартует, у него Cc = 0, а у сервера Cs уже не ноль.

Поэтому первый raw_1 = Cs - 0 получается огромный.

Если этот огромный raw_1 “запомнить” в EMA, то EMA ещё долго будет большой, и сервер будет присылать большие correction даже тогда, когда клиент уже синхронизировался.

Чтобы этого не было — мы сделали двухфазную логику.

4) Двухфазная логика NEW (то, что сейчас в коде)
У NEW теперь есть состояние на сервере для каждого клиента отдельно:

synced — был ли уже сделан “первый полный sync”
ema — сглаженная оценка остаточной ошибки после sync
Клиент идентифицируется ключом IP:port (UDP endpoint).

5) Фаза 1: “первый запрос = полная коррекция (как OLD)”
Условие
Если сервер видит клиента впервые (для его IP:port состояние synced == false):

Действие
Сервер делает:

[ correction = raw ]

То есть точно то же, что OLD.

Зачем
Это быстро ставит клиента “примерно в серверное время” за один шаг. После этого raw обычно становится маленьким, и можно уже сглаживать мелочи.

Что происходит со state
synced = true
ema = 0.0
Мы специально ставим ema в ноль: “после полного выравнивания остаточная ошибка ожидается около нуля, вот от этого и начинаем фильтрацию”.

6) Фаза 2: “последующие запросы = EMA только по маленькому остатку”
После первого полного sync клиент уже близко к серверу.

Теперь на каждом запросе:

сервер снова считает raw = Cs - Cc (теперь он обычно небольшой)
обновляет EMA:
[ ema \leftarrow ema + \alpha (raw - ema) ]

В коде (\alpha = 0.2).

отправляет:
[ correction = round(ema) ]

Смысл EMA тут
Теперь EMA работает как “фильтр” маленькой ошибки:

если raw прыгает из‑за сети +8, -3, +10, ...
EMA будет выдавать более гладкое: +6, +4, +5, ...
Клиент перестаёт “дёргаться” на каждом измерении.

7) Почему после первой коррекции correction станет маленьким (как ты и хотел)
После первой коррекции клиент делает:

[ Cc \leftarrow Cc + raw = Cc + (Cs - Cc) = Cs ]

То есть в идеале он становится ровно равен серверу (на момент измерения).

Дальше остаются только:

разница из‑за того, что пока пакет летел сервер уже чуть “ушёл вперёд”
неровность Sleep на клиенте
джиттер UDP
Эта остаточная ошибка обычно мала — именно её мы и фильтруем EMA во второй фазе.

8) Пример в цифрах (очень показательно)
Пусть Tc = 1000.

Первый запрос
Клиент: Cc = 0
Сервер сейчас: Cs = 300000
raw_1 = 300000 - 0 = 300000
NEW (фаза 1): correction_1 = 300000
Клиент: Cc = 0 + 300000 = 300000
Sleep 1000 → Cc = 301000
Второй запрос
Сервер за это время тоже примерно на 1000 ушёл, допустим:

Сервер: Cs ≈ 301010 (чуть больше из‑за задержки)
Клиент прислал: Cc = 301000
raw_2 = 10
Теперь NEW уже в фазе 2:

ema_0 = 0
ema_1 = 0 + 0.2*(10 - 0) = 2
correction_2 ≈ 2
Клиент:

Cc = 301000 + 2 = 301002
Sleep 1000 → Cc = 302002
Третий запрос
Допустим raw_3 = 7:

ema_2 = 2 + 0.2*(7-2) = 3
correction_3 ≈ 3
Видишь: после первого большого прыжка коррекции становятся маленькими и плавными.

9) Что именно отличается от OLD
OLD
Всегда: [ correction = raw ]

То есть каждый скачок raw сразу отражается на correction.

NEW (эта версия)
1‑й запрос клиента: correction = raw (как OLD)
дальше: correction = EMA(raw) (сглаженный raw)
То есть NEW — это “OLD + фильтр на хвосте”.

10) Важные ограничения (чтобы ты понимал поведение)
Ключ клиента = IP:port.
Если клиентский UDP порт поменяется (иногда ОС может поменять, если ты пересоздал сокет), сервер решит, что это “новый клиент” → снова будет “первая” большая коррекция.

(\alpha = 0.2) можно менять:

больше → быстрее реагирует, меньше сглаживает
меньше → сильнее сглаживает, но медленнее “догоняет” остаточную ошибку
time_ntp и шкала времени.
Если сервер работает в time_ntp (Unix ms), а клиентский Cc всё ещё “с нуля” и тикает Tc, то первая коррекция будет гигантская (это нормально — он должен прыгнуть в Unix‑время). После этого дальше снова будут маленькие.

11) Где это в коде (коротко)
В ConcurrentServer.cpp внутри ResponseServer:

первый sync → correction = rawCorrection, synced=true, ema=0
дальше EMA → correction = round(ema)
Это именно та логика, которую ты сейчас тестируешь.
