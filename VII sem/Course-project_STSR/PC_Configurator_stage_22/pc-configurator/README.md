# PC Configurator

Веб-приложение для подбора комплектующих персонального компьютера, создания конфигурации и сохранения сборок пользователя. Это учебный проект; текущий рабочий архив — **этап 21**.

## 1. Технологии

- **Frontend:** React, TypeScript, Vite.
- **Backend:** Node.js, NestJS, REST API.
- **База данных:** Microsoft SQL Server 2022 Developer.
- **Доступ к данным:** TypeORM (`mssql`).
- **Запуск:** Docker Compose.
- **API-префикс:** `/api/v1`.

## 2. Быстрый запуск в Windows

Нужен установленный и запущенный Docker Desktop с поддержкой Linux-контейнеров. Отдельно устанавливать Node.js для запуска через Docker не требуется.

1. Распаковать архив.
2. Открыть PowerShell в папке `pc-configurator` — там должен находиться `docker-compose.yml`.
3. При первом запуске проверить настройки `.env`. Если файла `.env` нет, создать его на основе `.env.example`:

   ```powershell
   Copy-Item .env.example .env
   ```

4. Запустить приложение:

   ```powershell
   docker compose up --build -d
   ```

5. Открыть адреса:

   - Сайт: <http://localhost:5173>
   - Проверка API: <http://localhost:3000/api/v1/health>
   - Каталог API: <http://localhost:3000/api/v1/components>

Полезные команды из корневой папки проекта:

```powershell
docker compose ps
docker compose logs --since 15m api
docker compose logs --since 15m web
docker compose up --build -d
docker compose down
```

`docker compose down` останавливает и удаляет контейнеры, но сохраняет данные в томе базы данных. **Не используй `docker compose down -v`, если не хочешь удалить данные базы.** Не удаляй контейнер `pc-configurator-db` вручную без необходимости: это может привести к конфликтам имён или потере доступа к существующим данным.

## 3. Переменные окружения и администратор

Настройки Docker Compose читаются из `.env`. Основные переменные:

- `MSSQL_SA_PASSWORD` — пароль SQL Server;
- `MSSQL_DATABASE` — имя базы данных;
- `DB_SYNCHRONIZE` — автоматическая синхронизация схемы TypeORM;
- `JWT_SECRET` — секрет подписи токенов;
- `ADMIN_EMAIL` и `ADMIN_PASSWORD` — учётные данные начального администратора.

В конфигурации для локальной разработки заданы демонстрационные значения по умолчанию. Перед публикацией проекта необходимо заменить пароли и `JWT_SECRET`. Не помещай реальные секреты в README или публичный репозиторий.

Если администратор не может войти или не создался, сначала проверь настройки `.env` и логи API:

```powershell
docker compose logs --since 15m api
```

Не предполагай, что изменение `ADMIN_PASSWORD` автоматически меняет пароль уже существующего пользователя: сначала нужно проверить логику и состояние учётной записи.

## 5. Что реализовано на этапе 21

### Каталог комплектующих

- Просмотр каталога, поиск и фильтрация по категории и цене.
- Категории: процессоры, видеокарты, материнские платы, оперативная память, накопители, охлаждение, блоки питания и корпуса.
- Карточка подробных характеристик комплектующей.
- Административные операции создания, редактирования и удаления комплектующих.
- Иконка-заполнитель выбирается по категории, если у комплектующей нет изображения.
- Импорт технических характеристик из BuildCores OpenDB доступен администратору.

### Аккаунты и сохранённые сборки

- Регистрация и вход по email и паролю; пароль хранится в виде хеша.
- Роли `USER` и `ADMIN`; административные операции каталога защищены на стороне API.
- Гость может временно собирать компьютер. Для сохранения сборки нужен вход в аккаунт.
- Пользователь может сохранить сборку, открыть её в редакторе и удалить.
- При сохранении сборки под уже существующим названием запрашивается подтверждение замены.
- Подтверждение удаления и обновления показывается в модальном окне по центру экрана с затемнением и размытием фона.

### Конфигуратор

- Добавление и удаление выбранных комплектующих.
- Отображение выбранных компонентов по категориям; пустая категория показывает «Не выбрано».
- Подсчёт общей стоимости выбранных компонентов.
- Значение `powerW` учитывается как мощность блока питания, а не как сумма TDP процессора и видеокарты.
- Выравнивание строк текущей сборки по горизонтали.

**Важно:** полноценная проверка совместимости компонентов пока не реализована. Суммарная стоимость и данные о мощности сами по себе не подтверждают, что комплектующие совместимы друг с другом или что выбранного блока питания достаточно.

## 6. API и доступ

Основные маршруты:

- `GET /api/v1/health` — проверка состояния API.
- `GET /api/v1/categories` — категории.
- `GET /api/v1/components` — каталог; поддерживаются фильтры, реализованные в DTO запроса.
- `GET /api/v1/components/:id` — одна комплектующая.
- `POST /api/v1/auth/register` — регистрация.
- `POST /api/v1/auth/login` — вход.
- `GET /api/v1/auth/me` — текущий пользователь с JWT.
- `GET /api/v1/configurations` — сборки текущего пользователя.
- `POST /api/v1/configurations` — создание сборки.
- `PATCH /api/v1/configurations/:id` — обновление сборки.
- `DELETE /api/v1/configurations/:id` — удаление сборки.

Создание, редактирование и удаление комплектующих доступны только администратору. Маршруты сохранённых сборок требуют авторизации и должны ограничивать доступ записями текущего пользователя. Для точной схемы маршрутов и полей проверяй актуальные контроллеры и DTO в `apps/api/src/`.

## 7. Импорт BuildCores OpenDB

Источник данных: <https://github.com/buildcores/buildcores-open-db>.

1. Запустить приложение и войти под администратором.
2. Открыть каталог и выбрать **«Импортировать OpenDB»**.
3. Подтвердить импорт и дождаться результата API.

Импорт требует доступа API-контейнера к интернету. Источник не предоставляет цены для используемого набора данных, поэтому цена может остаться пустой. При повторном импорте существующие записи должны обновляться по идентификаторам источника, а не дублироваться.

Если импорт завершается ошибкой тайм-аута, не запускай его многократно вслепую. Сначала посмотри `docker compose logs --since 15m api` и проверь, какие записи уже появились. Если обнаружены дубликаты, сначала нужно установить, по каким полям они идентифицируются, и только затем решать вопрос очистки.

Учитывай лицензию OpenDB перед распространением данных: <https://creativecommons.org/licenses/by-nc-sa/4.0/>. Проверь актуальные условия источника для предполагаемого использования.

## 8. Известные ограничения и осторожность

- Полная проверка совместимости комплектующих ещё не сделана.
- Требуется проверить импорт OpenDB на повторных запусках и убедиться, что не появляются дубликаты.
- Возможны сетевые тайм-ауты при импорте внешних данных.
- Нужно отдельно проверить создание начального администратора, особенно после изменения `.env` или пересоздания контейнеров.
- В проекте пока используется `DB_SYNCHRONIZE` для автоматической синхронизации схемы. Перед серьёзным развёртыванием следует подготовить миграции TypeORM и отключить автоматическую синхронизацию.
- Наличие функции в интерфейсе не заменяет проверку API, сборки TypeScript и ручное тестирование в браузере.

## 9. История последних изменений

- **Этап 15:** уменьшено мерцание активного пункта боковой навигации во время прокрутки.
- **Этап 16:** улучшено сопоставление записей при повторном импорте OpenDB, чтобы обновлять существующие компоненты вместо повторного добавления.
- **Этап 17:** обновлены названия и порядок пунктов меню: «Комплектующие», «Конфигуратор», «Сохранённые сборки».
- **Этап 18:** добавлено подтверждение удаления сохранённой сборки.
- **Этап 19:** текст подтверждения удаления перенесён на отдельные строки, кнопки выровнены по горизонтали.
- **Этап 20:** подтверждения удаления и обновления сборки вынесены в центральное модальное окно; улучшено горизонтальное выравнивание текущей сборки.
- **Этап 21:** для комплектующих без фотографии добавлены иконки по категории.

Это краткая история последних этапов, а не полный журнал Git.

## 10. Рекомендуемый следующий этап

Логичный следующий этап — **проверка совместимости компонентов** и отображение понятных предупреждений в конфигураторе. До начала реализации:

1. Изучить фактическую модель `Component`, категории и поля `specifications` в API.
2. Проверить, какие характеристики реально присутствуют после импорта OpenDB, а какие отсутствуют или имеют разный формат.
3. Определить минимальный набор проверок, который можно надёжно выполнить по доступным данным: сокет CPU и материнской платы, тип памяти, форм-фактор платы и корпуса, длина видеокарты и доступное место, а также требования к питанию.
4. Размещать бизнес-правила на сервере, а в интерфейсе показывать результат и объяснение предупреждений. Не объявлять компоненты совместимыми, если для проверки не хватает данных.
5. Добавить тесты для совместимых, несовместимых и неполных данных.

Это предложение по следующему этапу, а не уже реализованная функциональность. При новом запросе сначала уточни, хочет ли пользователь начать именно с совместимости или поставить другую задачу.
