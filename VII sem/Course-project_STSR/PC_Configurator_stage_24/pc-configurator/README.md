# PC Configurator

Веб-приложение для подбора комплектующих персонального компьютера, создания конфигурации и сохранения сборок пользователя. Это учебный проект; текущий рабочий архив — **этап 24**.

## 1. Технологии

- **Frontend:** React, TypeScript, Vite.
- **Backend:** Node.js, NestJS, REST API.
- **База данных:** Microsoft SQL Server 2022 Developer.
- **Доступ к данным:** TypeORM (`mssql`).
- **Запуск:** Docker Compose.
- **API-префикс:** `/api/v1`.

## 2. Быстрый запуск в Windows

Нужен установленный и запущенный Docker Desktop с поддержкой Linux-контейнеров. Отдельно устанавливать Node.js для запуска через Docker не требуется.

1. Распаковать архив.
2. Открыть PowerShell в папке `pc-configurator` — там должен находиться `docker-compose.yml`.
3. При первом запуске проверить настройки `.env`. Если файла `.env` нет, создать его на основе `.env.example`:

   ```powershell
   Copy-Item .env.example .env
   ```

4. Запустить приложение:

   ```powershell
   docker compose up --build -d
   ```

5. Открыть адреса:

   - Сайт: <http://localhost:5173>
   - Проверка API: <http://localhost:3000/api/v1/health>
   - Каталог API: <http://localhost:3000/api/v1/components>

Полезные команды из корневой папки проекта:

```powershell
docker compose ps
docker compose logs --since 15m api
docker compose logs --since 15m web
docker compose up --build -d
docker compose down
```

`docker compose down` останавливает и удаляет контейнеры, но сохраняет данные в томе базы данных. **Не используй `docker compose down -v`, если не хочешь удалить данные базы.** Не удаляй контейнер `pc-configurator-db` вручную без необходимости: это может привести к конфликтам имён или потере доступа к существующим данным.

## 3. Переменные окружения и администратор

Настройки Docker Compose читаются из `.env`. Основные переменные:

- `MSSQL_SA_PASSWORD` — пароль SQL Server;
- `MSSQL_DATABASE` — имя базы данных;
- `DB_SYNCHRONIZE` — автоматическая синхронизация схемы TypeORM;
- `JWT_SECRET` — секрет подписи токенов;
- `ADMIN_EMAIL` и `ADMIN_PASSWORD` — учётные данные начального администратора.

В конфигурации для локальной разработки заданы демонстрационные значения по умолчанию. Перед публикацией проекта необходимо заменить пароли и `JWT_SECRET`. Не помещай реальные секреты в README или публичный репозиторий.

Если администратор не может войти или не создался, сначала проверь настройки `.env` и логи API:

```powershell
docker compose logs --since 15m api
```

Не предполагай, что изменение `ADMIN_PASSWORD` автоматически меняет пароль уже существующего пользователя: сначала нужно проверить логику и состояние учётной записи.

## 5. Что реализовано на этапе 22

### Каталог комплектующих

- Просмотр каталога, поиск и фильтрация по категории и цене.
- Категории: процессоры, видеокарты, материнские платы, оперативная память, накопители, охлаждение, блоки питания и корпуса.
- Карточка подробных характеристик комплектующей.
- Административные операции создания, редактирования и удаления комплектующих.
- Иконка-заполнитель выбирается по категории, если у комплектующей нет изображения.
- Импорт технических характеристик из BuildCores OpenDB доступен администратору.

### Аккаунты и сохранённые сборки

- Регистрация и вход по email и паролю; пароль хранится в виде хеша.
- Роли `USER` и `ADMIN`; административные операции каталога защищены на стороне API.
- Гость может временно собирать компьютер. Для сохранения сборки нужен вход в аккаунт.
- Пользователь может сохранить сборку, открыть её в редакторе и удалить.
- При сохранении сборки под уже существующим названием запрашивается подтверждение замены.
- Подтверждение удаления и обновления показывается в модальном окне по центру экрана с затемнением и размытием фона.

### Конфигуратор

- Добавление и удаление выбранных комплектующих.
- Отображение выбранных компонентов по категориям; пустая категория показывает «Не выбрано».
- Подсчёт общей стоимости выбранных компонентов.
- Значение `powerW` учитывается как мощность блока питания, а не как сумма TDP процессора и видеокарты.
- Выравнивание строк текущей сборки по горизонтали.

### Проверка совместимости

- Серверный маршрут `POST /api/v1/components/compatibility` проверяет выбранные компоненты по идентификаторам из каталога.
- Проверяются сокет CPU и материнской платы, тип RAM и платы, форм-фактор платы и корпуса, габариты видеокарты и кулера относительно корпуса, поддержка сокета кулером и запас мощности БП для TDP CPU/GPU.
- В конфигураторе результат обновляется после изменения сборки: критические конфликты показываются как ошибки, а отсутствующие характеристики — как предупреждения.
- При неполных данных сборка не объявляется совместимой.
- Предупреждения о габаритах называют отсутствующую характеристику, например высоту кулера или допустимую высоту корпуса.
- Для оперативной памяти, охлаждения и накопителей можно выбрать количество от 1 до 10; оно учитывается в стоимости и сохраняется в конфигурации.
- Контекстный фильтр видеокарт использует объём видеопамяти из формата OpenDB.

### Цены и изображения

- Администратор может выбрать «Обновить цены и изображения»: Onliner используется для цен и предложений магазинов, Open Icecat — для фотографий товара.
- Icecat XML обрабатывается по структуре `ProductGallery/ProductPicture`: учитываются `IsMain`, `No`, `Pic` (полное изображение) и `Pic500x500` (изображение для карточки). До 12 фотографий сохраняются в исходном порядке, главное изображение ставится первым.
- Для карточек используются отдельные поля `imagePreviewUrl/imagePreviewUrls`; подробная галерея использует `imageUrl/imageUrls`. Если Icecat не вернул фото, интерфейс использует имеющееся полное изображение как резервное.
- Галереи не затираются одиночным изображением из другого источника. Изображения Open Icecat имеют приоритет, а найденные изображения Onliner и прайс-листов могут дополнять галерею.
- Поиск Onliner сначала использует MPN, а при его отсутствии требует сильного совпадения токенов модели и производителя. Это снижает риск перепутать похожие модификации, но может увеличить количество пропусков.
- Цены и предложения магазинов сохраняются отдельно; в карточке подробностей показываются магазин, цена и ссылка, если она присутствует в источнике. Для каждого основного значения цены хранятся источник, ссылка и дата обновления.
- Администратор может загрузить CSV или XLSX прайс-лист через «Импортировать прайс-лист». Обязательная колонка — `partNumber`, `mpn` или `артикул`; сопоставление выполняется по MPN и, если задан, производителю. Поддерживаются колонки `manufacturer`, `price`, `productUrl`, `imageUrl`, `imageUrls`, `shop`, `offerUrl`. Несколько строк с одним MPN и разными магазинами добавляют несколько предложений. Несколько URL в `imageUrls` можно разделять символом `|`.
- Размер загружаемого прайс-листа ограничен 5 МБ. Импортёр не создаёт новые комплектующие и пропускает строки без однозначного совпадения по артикулу.
- Для Open Icecat нужны XML-учётные данные в `.env`: `ICECAT_USERNAME` и `ICECAT_PASSWORD`. Поиск выполняется по производителю и MPN; записи без MPN или без покрытия в Open Icecat пропускаются.
- Open Icecat является источником контента и изображений, а не локальных розничных цен. Для дополнительных цен можно загружать прайс-листы поставщиков. Например, OnLife публикует XLSX-каталог, а ГК Центра предоставляет CSV-прайсы организациям по запросу. Условия и актуальность цен нужно проверять у поставщика. Kramba показывает агрегированные предложения партнёрских магазинов, но отдельный стабильный API или официальный файл выгрузки для интеграции в проект не подтверждён; поэтому прямой парсер Kramba не добавлялся.
- Внешние изображения пока хранятся как URL источника, а не скачиваются в собственное файловое хранилище. Ссылки Icecat могут изменяться, поэтому для публичного развёртывания в будущем стоит добавить локальное хранение изображений.

## 6. API и доступ

Основные маршруты:

- `GET /api/v1/health` — проверка состояния API.
- `GET /api/v1/categories` — категории.
- `GET /api/v1/components` — каталог; поддерживаются фильтры, реализованные в DTO запроса.
- `GET /api/v1/components/:id` — одна комплектующая.
- `POST /api/v1/components/import/catalog-data` — импорт JSON-строк прайс-листа (администратор).
- `POST /api/v1/components/import/catalog-file` — загрузка CSV/XLSX (multipart/form-data, поле `file`, необязательное поле `source`; администратор).
- `POST /api/v1/components/import/catalog-enrichment` — обновление Onliner и Open Icecat (администратор).
- `POST /api/v1/auth/register` — регистрация.
- `POST /api/v1/auth/login` — вход.
- `GET /api/v1/auth/me` — текущий пользователь с JWT.
- `GET /api/v1/configurations` — сборки текущего пользователя.
- `POST /api/v1/configurations` — создание сборки.
- `PATCH /api/v1/configurations/:id` — обновление сборки.
- `DELETE /api/v1/configurations/:id` — удаление сборки.

Создание, редактирование и удаление комплектующих доступны только администратору. Маршруты сохранённых сборок требуют авторизации и должны ограничивать доступ записями текущего пользователя. Для точной схемы маршрутов и полей проверяй актуальные контроллеры и DTO в `apps/api/src/`.

## 7. Импорт BuildCores OpenDB

Источник данных: <https://github.com/buildcores/buildcores-open-db>.

1. Запустить приложение и войти под администратором.
2. Открыть каталог и выбрать **«Импортировать OpenDB»**.
3. Подтвердить импорт и дождаться результата API.

Импорт требует доступа API-контейнера к интернету. Источник не предоставляет цены для используемого набора данных, поэтому цена может остаться пустой. При повторном импорте существующие записи должны обновляться по идентификаторам источника, а не дублироваться.

Если импорт завершается ошибкой тайм-аута, не запускай его многократно вслепую. Сначала посмотри `docker compose logs --since 15m api` и проверь, какие записи уже появились. Если обнаружены дубликаты, сначала нужно установить, по каким полям они идентифицируются, и только затем решать вопрос очистки.

Учитывай лицензию OpenDB перед распространением данных: <https://creativecommons.org/licenses/by-nc-sa/4.0/>. Проверь актуальные условия источника для предполагаемого использования.

## 8. Известные ограничения и осторожность

- Проверка основана только на `specifications`; она не заменяет документацию производителя и пока не охватывает все ограничения (PCIe, разъёмы питания, версии BIOS и другие).
- Требуется проверить импорт OpenDB на повторных запусках и убедиться, что не появляются дубликаты.
- Возможны сетевые тайм-ауты при импорте внешних данных.
- Нужно отдельно проверить создание начального администратора, особенно после изменения `.env` или пересоздания контейнеров.
- В проекте пока используется `DB_SYNCHRONIZE` для автоматической синхронизации схемы. Перед серьёзным развёртыванием следует подготовить миграции TypeORM и отключить автоматическую синхронизацию.
- Наличие функции в интерфейсе не заменяет проверку API, сборки TypeScript и ручное тестирование в браузере.

## 10. Рекомендуемый следующий этап

Логичный следующий этап — расширить покрытие проверки совместимости: добавить автоматические тесты для совместимых, несовместимых и неполных данных, а также правила для разъёмов питания, накопителей, PCIe и BIOS при наличии надёжных данных.

1. Изучить фактическую модель `Component`, категории и поля `specifications` в API.
2. Проверить, какие характеристики реально присутствуют после импорта OpenDB, а какие отсутствуют или имеют разный формат.
3. Определить минимальный набор проверок, который можно надёжно выполнить по доступным данным: сокет CPU и материнской платы, тип памяти, форм-фактор платы и корпуса, длина видеокарты и доступное место, а также требования к питанию.
4. Размещать бизнес-правила на сервере, а в интерфейсе показывать результат и объяснение предупреждений. Не объявлять компоненты совместимыми, если для проверки не хватает данных.
5. Добавить тесты для совместимых, несовместимых и неполных данных.

Проверка должна по-прежнему выполняться на сервере, а интерфейс должен только показывать её результат и понятные пояснения.

## Stage 10 — каталог, галерея и предложения магазинов

Перед запуском обновлённой версии API один раз выполните SQL-скрипт
`database/stage_10_catalog_gallery.sql` в базе `PCConfigurator`. Он добавляет
поля `image_urls` и `price_offers`, а также переносит уже имеющееся главное
изображение в галерею, чтобы старые записи не потеряли фотографии.

После миграции:
- каталог отображается компактными карточками с адаптивной сеткой;
- в карточке показывается основное фото, а в подробном окне можно переключать
  дополнительные изображения;
- загрузчик Open Icecat сохраняет все найденные изображения товара, а не только
  главное; загрузчик Onliner также сохраняет несколько изображений, если они
  присутствуют в ответе каталога;
- найденные предложения магазинов сохраняются отдельно от основной цены и
  отображаются в подробностях комплектующей;
- обновление цен Onliner выполняется даже при отсутствии учётных данных Open
  Icecat. Для загрузки дополнительных изображений Icecat по-прежнему нужны
  `ICECAT_USERNAME` и `ICECAT_PASSWORD`.

Количество цен и фотографий по-прежнему зависит от наличия соответствующих
данных у внешних каталогов. Приложение не подставляет вымышленные цены или
изображения; при отсутствии подтверждённого совпадения поле остаётся пустым.


## 11. Stage 24 — дополнительные замечания по импорту

Для ручного импорта прайс-листа пример структуры находится в `docs/catalog-data-import-example.csv`. Если в файле одна позиция повторяется для нескольких магазинов, указывайте один и тот же MPN в нескольких строках и отдельное значение `shop` для каждой строки. Не указывайте произвольный MPN: без точного совпадения с данными OpenDB/каталога позиция будет пропущена.

После распаковки Stage 24:
1. Если `DB_SYNCHRONIZE=true`, новые поля превью будут созданы TypeORM при запуске API.
2. Если автоматическая синхронизация отключена, один раз выполните `database/stage_24_catalog_previews.sql` в базе `PCConfigurator`.
3. Проверьте `ICECAT_USERNAME` и `ICECAT_PASSWORD` в `.env`.
4. Пересоберите контейнеры командой `docker compose up --build -d`.
5. Войдите администратором, откройте каталог и запустите «Обновить цены и изображения». Для внешнего прайс-листа используйте «Импортировать прайс-лист».

Импортёр не обещает наличие предложения, если источник его не возвращает. Отсутствующая цена остаётся пустой; цены из файлов поставщиков считаются данными указанного прайса и могут требовать подтверждения продавца.
