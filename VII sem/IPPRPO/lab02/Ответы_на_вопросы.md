**1. Что такое Apache Maven?**

&#x09;Apache Maven — это инструмент автоматизации сборки Java-проектов. Он позволяет управлять структурой проекта, зависимостями, компиляцией, тестированием и упаковкой приложения в JAR-файл.



**2. Зачем Maven нужен в промышленной разработке?**

&#x09;Maven автоматизирует стандартные операции разработки: сборку проекта, подключение библиотек, запуск тестов и создание готовых артефактов. Это делает процесс сборки одинаковым для разных разработчиков и упрощает автоматизацию в CI/CD.



**3. Для чего используется pom.xml?**

&#x09;pom.xml — главный конфигурационный файл Maven-проекта. В нем описываются идентификаторы проекта, версия, зависимости, плагины и настройки сборки.



**4. Что такое groupId, artifactId и version?**

groupId — идентификатор организации или пространства имен проекта.

artifactId — имя проекта и создаваемого Maven-артефакта.

version — версия проекта.

Вместе эти параметры однозначно определяют Maven-артефакт.



**5. Что такое Maven dependency?**

&#x09;Dependency — это внешняя зависимость проекта, то есть библиотека, которая необходима приложению или тестам. Зависимости указываются в pom.xml, после чего Maven самостоятельно получает их из репозитория.



**6. Откуда Maven получает зависимости?**

&#x09;По умолчанию Maven получает зависимости из центрального Maven-репозитория. После загрузки зависимости сохраняются в локальном репозитории пользователя и могут использоваться при последующих сборках.



**7. Для чего нужен src/main/java?**

&#x09;Каталог src/main/java предназначен для основного исходного кода Java-приложения.



**8. Для чего нужен src/test/java?**

&#x09;Каталог src/test/java предназначен для исходного кода автоматизированных тестов. Эти тесты используются Maven при выполнении фазы test.



**9. Для чего используется каталог target?**

&#x09;Каталог target содержит результаты работы Maven: скомпилированные классы, результаты тестирования и созданные артефакты, например JAR-файл.



**10. Где должны находиться ресурсы приложения?**

&#x09;Ресурсы приложения должны находиться в каталоге src/main/resources. Maven копирует их в результат сборки.



**11. Что происходит при выполнении mvn compile?**

&#x09;Maven выполняет фазу compile и компилирует основной исходный код проекта из src/main/java. Результат помещается в каталог target/classes.



**12. Что происходит при выполнении mvn test?**

&#x09;Maven компилирует тесты, запускает автоматизированные тесты и формирует результаты тестирования. Если тест завершается ошибкой, сборка на этой фазе считается неуспешной.



**13. Что делает mvn package?**

&#x09;Maven выполняет необходимые предыдущие фазы жизненного цикла, включая компиляцию и тестирование, а затем упаковывает проект в указанный артефакт. Для Java-проекта обычно создается JAR-файл в каталоге target.



**14. Чем package отличается от install?**

&#x09;Фаза package создает готовый артефакт проекта в каталоге target.

&#x09;Фаза install выполняет package и дополнительно устанавливает созданный артефакт в локальный Maven-репозиторий, чтобы его могли использовать другие локальные Maven-проекты.



**15. Что произойдет, если один из тестов завершится ошибкой?**

&#x09;Maven сообщит об ошибке тестирования, а соответствующая фаза завершится неуспешно. При обычной сборке следующие этапы, зависящие от успешного прохождения тестов, выполнены не будут.



**16. Зачем зависимости указываются в pom.xml?**

&#x09;Чтобы Maven знал, какие библиотеки необходимы проекту, мог автоматически скачать их и добавить в classpath во время компиляции, тестирования или запуска.



**17. Зачем указывать версию зависимости?**

&#x09;Версия определяет конкретный вариант библиотеки, который должен использоваться проектом. Это обеспечивает предсказуемость и воспроизводимость сборки.



**18. Что такое транзитивные зависимости?**

&#x09;Транзитивные зависимости — это библиотеки, которые необходимы не непосредственно нашему проекту, а одной из его зависимостей. Maven автоматически учитывает такие зависимости.



**19. Чем зависимость для production-кода может отличаться от зависимости для тестов?**

&#x09;Зависимость production-кода нужна непосредственно приложению во время его работы. Тестовая зависимость нужна для разработки и запуска тестов и обычно не должна попадать в рабочее приложение. В Maven для этого используется, например, scope test.



**20. Почему Maven удобнее ручного подключения JAR-файлов?**

&#x09;Maven автоматически загружает зависимости, учитывает их версии и транзитивные зависимости, а также позволяет одинаково собирать проект на разных компьютерах. Не нужно вручную скачивать и подключать отдельные JAR-файлы.



**21. Как Maven может использоваться внутри CI/CD?**

&#x09;В CI/CD Maven может автоматически выполнять сборку проекта, запускать тесты, проверять результат и создавать JAR-файлы. Например, сервер непрерывной интеграции может выполнять команды mvn test или mvn package при каждом изменении исходного кода.



**22. Что произойдет, если другой разработчик клонирует ваш проект?**

&#x09;После клонирования разработчик получает исходный код и pom.xml. Maven прочитает pom.xml, автоматически загрузит необходимые зависимости и сможет собрать проект стандартными командами Maven.



**23. Какие действия ему достаточно выполнить, чтобы получить собранный проект?**

&#x09;Необходимо открыть проект в среде разработки или терминале, убедиться, что установлен JDK и Maven, а затем выполнить, например:

mvn clean package

После успешного выполнения JAR-файл будет находиться в каталоге target.



**24. Как Maven связан с Jenkins?**

&#x09;Jenkins может запускать Maven-команды автоматически в процессе CI/CD. Например, Jenkins может выполнить mvn clean test или mvn package после получения изменений из системы контроля версий, проверить тесты и получить готовый JAR-файл.





**ДОПОЛНИТЕЛЬНО: ВАРИАНТ 2 — MAVEN-ПЛАГИН**

&#x09;В варианте 2 необходимо подключить дополнительный Maven-плагин, объяснить его назначение и продемонстрировать результат его работы через Maven.

&#x09;В проекте используется maven-antrun-plugin. Он позволяет выполнять действия Apache Ant в рамках жизненного цикла Maven.

Плагин привязан к фазе verify. При выполнении команды: mvn clean verify

&#x09;Maven проходит жизненный цикл сборки, а на фазе verify запускается дополнительная настройка плагина. В результате создается файл: target/variant2-plugin-result.txt

&#x09;Этот файл является наглядным результатом работы дополнительного Maven-плагина.

**Для защиты можно объяснить:**

«Я подключил maven-antrun-plugin в pom.xml и привязал его выполнение к фазе verify. Плагин выполняет дополнительное действие после основных этапов сборки и создает файл variant2-plugin-result.txt в каталоге target. Таким образом, результат работы плагина можно проверить непосредственно после выполнения команды mvn clean verify.»
